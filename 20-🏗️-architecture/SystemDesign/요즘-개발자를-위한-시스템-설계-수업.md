# 5장. 시스템 구성요소의 설계 및 구현: 데이터베이스와 스토리지
## Q1. DynamoDB의 예시는? 언제 이 DB를 선택할까?
### DynamoDB란?
- AWS가 운영하는 **완전 관리형 키-값 / 문서형 NoSQL DB**
	- 서버, 패치, 복제, 확장을 AWS가 관리 → 운영 부담이 거의 없음
	- 데이터 크기와 상관없이 **한 자릿수 ms 수준의 일정한 응답 속도**를 목표로 설계됨
- 핵심 개념
	- **파티션 키(Partition Key)** : 해시해서 데이터가 저장될 파티션을 정함 → 수평 확장의 기준
	- **정렬 키(Sort Key)** : 같은 파티션 키 안에서 정렬해 범위 조회 가능 (예: `userId` + `createdAt`)
	- **GSI(Global Secondary Index)** : 다른 키로도 조회하고 싶을 때 쓰는 보조 인덱스

### 사용 예시
| 예시 | 키 설계 예 | DynamoDB가 맞는 이유 |
| --- | --- | --- |
| 쇼핑몰 장바구니 | PK=`userId` | 사용자 단위로 읽고 쓰기, 트래픽이 몰리는 시간대 대응 |
| 로그인 세션 저장소 | PK=`sessionId`, TTL 설정 | 키 하나로 조회, TTL로 만료된 항목 자동 삭제 |
| 게임 플레이어 상태 / 인벤토리 | PK=`playerId` | 쓰기가 많고 지연에 민감함 |
| IoT 센서·이벤트 로그 | PK=`deviceId`, SK=`timestamp` | 쓰기량이 많음, 기기별 시간 범위 조회 |
| 주문 상태 추적 | PK=`orderId` | 단건 조회·갱신이 대부분 |
- 원조 사례 : Amazon의 장바구니가 블랙프라이데이 트래픽에도 버티도록 만든 Dynamo 논문(2007)이 DynamoDB의 출발점

### 언제 선택할까?
- ✅ 선택하면 좋을 때
	- **조회 패턴이 단순하고 미리 정해져 있을 때** (대부분 "키로 찾기")
	- 트래픽이 아주 크거나, 갑자기 몰리는 등 **예측하기 어려울 때** (온디맨드 모드)
	- 데이터가 커져도 **응답 속도를 일정하게** 유지해야 할 때
	- DB 운영 인력이 부족하거나 서버리스(Lambda 등)로 구성할 때
- ❌ 피해야 할 때
	- **JOIN, 집계, 즉석(ad-hoc) 쿼리**가 많을 때 → RDB나 분석용 DB가 낫다
	- 조회 패턴이 아직 정해지지 않았을 때 → 나중에 바꾸려면 테이블을 다시 설계해야 한다
	- 여러 항목에 걸친 복잡한 트랜잭션이 핵심일 때 (트랜잭션을 지원하지만 제약이 있음)
	- 특정 키에 요청이 몰리는 구조일 때 → **핫 파티션(hot partition)** 문제
- 한 줄 요약 : **"어떻게 조회할지 먼저 정하고, 그에 맞춰 테이블을 설계한다"** (RDB는 반대로 데이터 구조를 먼저 정하고 쿼리를 나중에 짠다)

## Q2. 수직 분할과 수평 분할은 왜 하고, 언제 할까?
> 공통 목적 : **테이블 하나(또는 서버 하나)가 감당하기 어려울 만큼 커졌을 때 데이터를 나눠서** 성능과 확장성을 확보하기 위함

### 수직 분할 (Vertical Partitioning) — "열(column)을 나눈다"
- 하나의 테이블을 **컬럼 기준으로** 여러 테이블로 나눔
```
users(id, name, email, profile_image, bio, last_login)
  → users(id, name, email, last_login)       -- 자주 조회
  → user_profiles(id, profile_image, bio)    -- 가끔 조회, 크기가 큼
```
- 왜 할까?
	- 자주 읽는 컬럼만 남기면 **행이 작아져** 한 페이지·캐시에 더 많은 행이 들어감 → I/O 감소
	- 크기가 큰 컬럼(BLOB, TEXT)이나 잘 안 쓰는 컬럼을 떼어냄 (hot / cold 분리)
	- 민감한 컬럼(개인정보, 결제정보)을 따로 두어 **접근 권한 분리**
	- 서비스 수준에서는 기능별로 DB를 나눔 (회원 DB / 주문 DB) → 마이크로서비스 구조
- 언제?
	- 컬럼마다 **조회 빈도나 크기 차이가 클 때**
	- 행이 많아서가 아니라 **한 행이 너무 넓어서** 느릴 때
- 단점 : 전체 데이터를 다시 모으려면 JOIN이 필요함

### 수평 분할 (Horizontal Partitioning) — "행(row)을 나눈다"
- 스키마는 그대로 두고 **행을 특정 기준으로** 나눔
	- 여러 서버에 나누어 저장하면 **샤딩(Sharding)**이라고 부름
- 나누는 방식
	| 방식 | 예 | 장점 | 단점 |
	| --- | --- | --- | --- |
	| 범위(Range) | 2025년 주문 / 2026년 주문 | 범위 조회에 유리 | 최신 범위에 쓰기가 몰림 (핫스팟) |
	| 해시(Hash) | `hash(userId) % N` | 고르게 분산됨 | 범위 조회 불리, 샤드 수를 바꾸면 재배치 필요 → 일관된 해싱으로 완화 |
	| 목록(List) | 국가별 (KR / US / JP) | 데이터 지역성, 규제 대응 | 지역마다 크기가 고르지 않음 |
- 왜 할까?
	- 데이터 양이나 **쓰기 트래픽이 서버 한 대의 한계를 넘을 때** (읽기만 많다면 먼저 레플리카와 캐시로 해결 가능)
	- 테이블과 인덱스가 작아져 조회와 관리(백업, 오래된 데이터 삭제)가 빨라짐
- 언제?
	- 스케일 업(더 좋은 서버)과 읽기 레플리카로도 **더는 버티기 어려울 때** → 복잡도가 크게 늘어나므로 최후의 수단에 가까움
- 단점
	- 샤드를 넘나드는 **JOIN과 트랜잭션**이 어려움
	- **샤드 키**를 잘못 고르면 핫스팟이 생기고, 나중에 바꾸기가 매우 어려움
	- 샤드를 추가할 때 데이터 재배치(리밸런싱)가 필요함

### 한눈에 비교
| | 수직 분할 | 수평 분할 |
| --- | --- | --- |
| 나누는 단위 | 컬럼 | 행 |
| 스키마 | 테이블마다 다름 | 모든 파티션이 같음 |
| 해결하는 문제 | 한 행이 넓다 / 컬럼마다 접근 패턴이 다르다 | 행이 너무 많다 / 트래픽이 너무 많다 |
| 대표적인 비용 | JOIN 증가 | 샤드 간 쿼리·트랜잭션, 리밸런싱 |

- ⚠️ 헷갈리기 쉬운 것 : **수직 확장(Scale-up, 서버 사양 올리기)**이나 **수평 확장(Scale-out, 서버 늘리기)**과는 다른 개념이다. 수평 분할(샤딩)은 수평 확장을 *하기 위한* 방법 중 하나다.
- DynamoDB와의 연결 : DynamoDB는 **파티션 키 기반의 해시 수평 분할을 자동으로** 해 주는 DB다. 그래서 파티션 키 설계가 가장 중요하다.

## Q3. 그래프 DB vs 하둡 vs DynamoDB, 실무에서 더 많이 쓰이는 것은?
> 먼저 짚을 점 : 셋은 **해결하는 문제가 달라서** 서로 경쟁하는 관계가 아니다. "무엇이 더 낫나"보다 "어떤 문제에 쓰나"로 봐야 한다.

| | 그래프 DB (Neo4j, Amazon Neptune) | 하둡 (HDFS + MapReduce) | DynamoDB |
| --- | --- | --- | --- |
| 분류 | 관계 중심 DB | 대용량 **배치 처리·저장** 플랫폼 | 키-값 NoSQL (**서비스용 OLTP**) |
| 잘하는 것 | 여러 단계에 걸친 관계 탐색 (친구의 친구, 이상거래 연결 고리) | TB~PB 데이터를 한꺼번에 분석 | 키로 빠르게 읽고 쓰기, 무한에 가까운 확장 |
| 대표 사례 | 이상거래 탐지, 추천, 지식 그래프, 권한 그래프 | 로그 분석, ETL, 데이터 웨어하우스 원천 | 장바구니, 세션, 주문 상태, 게임 상태 |
| 요즘 추세 | 꾸준하지만 **특정 분야용** | **하락세** → Spark, S3 기반 데이터 레이크, Snowflake·BigQuery 같은 클라우드 DW로 대체되는 중 | **AWS 백엔드에서 매우 흔함** |

- 실무에서 마주칠 가능성 : **DynamoDB > 하둡 계열 > 그래프 DB**
	- 백엔드 개발자라면 DynamoDB(또는 비슷한 키-값 NoSQL)를 만날 가능성이 가장 높다.
	- 하둡 자체보다는 그 **개념**(HDFS의 분산 저장, MapReduce의 분산 처리)이 Spark와 데이터 레이크로 이어진다. 데이터 엔지니어링 쪽이라면 개념은 꼭 알아야 한다.
	- 그래프 DB는 문제가 "관계 탐색"일 때만 고르는 전문 도구다.

## Q4. 백엔드에서 DB 관련 이슈, 중요도 순으로 정리
> 중요도 기준 : **사고가 났을 때 피해 크기 × 실무에서 겪는 빈도**. 맨 위로 갈수록 "되돌릴 수 없는" 문제다.

### 🔴 1등급 — 데이터가 틀리거나 사라진다 (되돌리기 어려움)
| 순위 | 이슈 | 대표 증상 | 핵심 대처 |
| --- | --- | --- | --- |
| 1 | **동시성·정합성** | 재고가 마이너스, 포인트 중복 지급, 갱신 손실(lost update) | 트랜잭션, 격리 수준 이해, 비관적 락(`SELECT ... FOR UPDATE`)·낙관적 락(version 컬럼), 유니크 제약 |
| 2 | **백업·복구** | 실수로 지운 데이터를 되살릴 수 없음 | 자동 백업 + 시점 복구(PITR), **복구 훈련을 실제로 해 보기** |
| 3 | **보안** | SQL 인젝션, 개인정보 유출 | 바인딩 파라미터(PreparedStatement), 최소 권한 계정, 민감 정보 암호화 |
| 4 | **스키마 마이그레이션** | 큰 테이블에 `ALTER` → 테이블 락 → 서비스 멈춤 | 온라인 DDL 도구(gh-ost, pt-osc), 하위 호환되게 단계적으로 배포 (컬럼 추가 → 코드 배포 → 옛 컬럼 삭제) |

### 🟠 2등급 — 서비스가 느려지거나 멈춘다 (가장 자주 겪음)
| 순위 | 이슈 | 대표 증상 | 핵심 대처 |
| --- | --- | --- | --- |
| 5 | **느린 쿼리·인덱스** | 특정 API만 느림, DB CPU 급증 | 실행 계획(`EXPLAIN`) 확인, 인덱스 설계, 슬로우 쿼리 로그 모니터링 |
| 6 | **N+1 쿼리** | 목록 하나에 쿼리 수백 번 | fetch join, 배치 조회(`IN`), ORM이 만드는 쿼리 로그 확인 |
| 7 | **커넥션 풀 고갈** | 갑자기 전체 API가 타임아웃 | 풀 크기 조정, 쿼리·트랜잭션 타임아웃 설정, 트랜잭션 안에서 외부 API 호출 금지 |
| 8 | **락 대기·데드락** | 간헐적 실패, 응답이 들쭉날쭉 | 트랜잭션을 짧게, 자원 잠그는 순서를 통일, 긴 트랜잭션 모니터링 |

### 🟡 3등급 — 규모가 커지면 등장한다
| 순위 | 이슈 | 대표 증상 | 핵심 대처 |
| --- | --- | --- | --- |
| 9 | **복제 지연(Replication lag)** | 방금 쓴 글이 목록에 안 보임 | 쓰기 직후 조회는 primary에서 읽기 (read-your-writes) |
| 10 | **캐시와 DB 불일치** | 수정했는데 옛 값이 보임 | 캐시 무효화 전략, TTL, cache-aside 패턴 |
| 11 | **확장 한계** | 쓰기 트래픽·데이터 양이 서버 한 대를 넘음 | 레플리카 → 수직 분할 → 샤딩 순으로 (Q2 참고), 핫스팟 주의 |

### 정리
- 1등급은 **한 번만 터져도 치명적**이니 설계 단계에서 막아야 한다.
- 2등급은 **운영하면서 가장 많이 겪으니** 모니터링(슬로우 쿼리, 커넥션 수, 락 대기)을 기본으로 깔아 둔다.
- 3등급은 **필요해졌을 때** 도입한다. 미리 샤딩부터 하면 복잡도만 늘어난다.
