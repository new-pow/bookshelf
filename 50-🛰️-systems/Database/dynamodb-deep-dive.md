# 1. 내부 구조
## 1.1 기본 단위
| 용어 | RDB로 치면 | 설명 |
| --- | --- | --- |
| 테이블 | 테이블 | 스키마가 없음. 키만 정해 두면 항목마다 속성이 달라도 됨 |
| 항목(Item) | 행 | **최대 400KB** |
| 속성(Attribute) | 컬럼 | 문자열, 숫자, 리스트, 맵 등 |
| 기본 키 | PK | **파티션 키** 하나만 쓰거나, **파티션 키 + 정렬 키** 조합 |

## 1.2 파티션 — 수평 분할을 자동으로
```
PutItem(PK="USER#1", ...)
   │  hash("USER#1")
   ▼
┌─────────────┬─────────────┬─────────────┐
│ 파티션 A     │ 파티션 B     │ 파티션 C     │  ← 해시 범위별로 나뉨
│ USER#7 ...  │ USER#1 ...  │ USER#3 ...  │
└─────────────┴─────────────┴─────────────┘
```
- 파티션 키를 해시해서 **어느 파티션에 저장할지** 정한다 → 5장 Q2의 해시 기반 수평 분할(샤딩)
- 같은 파티션 키를 가진 항목들은 한 파티션 안에 **정렬 키 순서로** 저장된다 → 범위 조회가 빠른 이유
- 파티션 하나의 한계 (대략적인 값)
	- 저장 용량 약 **10GB**
	- 처리량 초당 **읽기 3,000 RCU / 쓰기 1,000 WCU**
	- 한계에 가까워지면 DynamoDB가 **파티션을 자동으로 쪼갠다**. 개발자는 파티션 개수를 직접 관리하지 않는다.

## 1.3 복제 — 3개 가용 영역(AZ)
- 각 파티션은 **서로 다른 3개 AZ에 복제**된다 (복제본 묶음 = replication group)
- 복제본 중 하나가 **리더**이고, 리더는 Multi-Paxos 합의 알고리즘으로 뽑는다
	- **쓰기**는 리더가 받는다 → 복제본 3개 중 **2개에 기록되면** 성공으로 응답
	- **강한 일관성 읽기**는 리더에서 읽는다
	- **최종 일관성 읽기**는 아무 복제본에서나 읽는다 → 방금 쓴 값이 아직 안 보일 수 있다
- 그래서 AZ 하나가 통째로 죽어도 데이터는 살아남는다

## 1.4 비용 단위 (프로비저닝 모드 기준)
| 단위 | 의미 |
| --- | --- |
| 1 **RCU** | 4KB 이하 항목을 초당 **강한 일관성 읽기 1번** (최종 일관성이면 2번) |
| 1 **WCU** | 1KB 이하 항목을 초당 **쓰기 1번** |
- 트랜잭션 읽기·쓰기는 **2배**를 소모한다
- 용량 모드
	| 모드 | 언제 |
	| --- | --- |
	| 온디맨드 | 트래픽을 예측하기 어려울 때, 새 서비스. 요청한 만큼 과금 |
	| 프로비저닝 (+ 오토스케일링) | 트래픽이 일정할 때. 미리 정한 만큼 과금, 보통 더 저렴 |

# 2. 일관성과 트랜잭션
## 2.1 읽기 일관성
| | 최종 일관성 (기본값) | 강한 일관성 |
| --- | --- | --- |
| 읽는 곳 | 아무 복제본 | 리더 |
| 비용 | 0.5 RCU / 4KB | 1 RCU / 4KB |
| 방금 쓴 값 | 안 보일 수 있음 (보통 1초 안에 반영) | 항상 보임 |
| GSI에서 | 가능 | **불가능** (GSI는 최종 일관성만) |
- 실무 감각 : 대부분은 최종 일관성으로 충분하다. "쓰고 바로 읽어서 판단"하는 곳(결제 직후 상태 확인 등)만 강한 일관성을 쓴다.

## 2.2 조건부 쓰기 — 낙관적 락
- `ConditionExpression`으로 "조건이 맞을 때만 쓰기"
```
UpdateItem
  Key: { PK: "PRODUCT#p1" }
  UpdateExpression:    "SET stock = stock - :q, version = version + :one"
  ConditionExpression: "stock >= :q AND version = :v"
```
- 조건이 틀리면 `ConditionalCheckFailedException` → 다시 읽고 재시도
- 5장 Q4의 1등급 이슈(동시성·정합성)를 DynamoDB에서는 이렇게 막는다
- 숫자 하나만 올리고 내릴 거라면 `ADD count :1`(원자적 카운터)로 충분하다

## 2.3 트랜잭션
- `TransactWriteItems` / `TransactGetItems` : **최대 100개 항목**을 전부 성공하거나 전부 실패하게 처리
	- 여러 테이블에 걸쳐도 된다
	- 비용 2배, 같은 항목에 동시에 요청하면 충돌로 실패할 수 있다
- RDB처럼 "트랜잭션을 열어 두고 여러 쿼리를 실행"하는 방식이 **아니다**. 요청 한 번에 묶어서 보낸다.

# 3. 테이블 설계 — 조회 패턴부터 정하기
## 3.1 RDB와 순서가 반대다
| | RDB | DynamoDB |
| --- | --- | --- |
| 설계 순서 | 데이터 구조(정규화) → 쿼리는 나중에 | **조회 패턴 목록** → 그에 맞는 키 |
| JOIN | 쿼리할 때 합친다 | 없음. **미리 합쳐서 저장**한다 (비정규화) |
| 새 조회 패턴이 생기면 | 쿼리만 새로 짜면 됨 | GSI 추가 또는 데이터 재설계 |

## 3.2 조회 방법
| 연산 | 조건 | 비용 |
| --- | --- | --- |
| `GetItem` | 기본 키 전체 | 항목 1개만큼 |
| `Query` | **파티션 키 필수** + 정렬 키 조건(`=`, `<`, `between`, `begins_with`) | 읽은 만큼 |
| `Scan` | 없음 (테이블 전체) | **테이블 전체만큼** → 서비스 경로에서 쓰지 않는다 |
- `Query`와 `Scan`은 한 번에 **최대 1MB**까지만 돌려준다 → `LastEvaluatedKey`로 다음 페이지를 이어서 읽는다
- `FilterExpression`은 **읽은 다음에** 걸러내므로 비용이 줄지 않는다

## 3.3 보조 인덱스
| | LSI (로컬) | GSI (글로벌) |
| --- | --- | --- |
| 키 | 파티션 키는 같고 **정렬 키만 다름** | 파티션 키부터 **완전히 다름** |
| 만드는 시점 | **테이블 만들 때만** | 언제든 추가 가능 |
| 일관성 | 강한 일관성 가능 | 최종 일관성만 |
| 제약 | 파티션 키 하나당 10GB | GSI도 자체 처리량을 쓴다 → GSI가 밀리면 원본 쓰기도 막힐 수 있음 |
- 실무에서는 **거의 GSI**를 쓴다

## 3.4 단일 테이블 설계 (Single-table design)
- 여러 종류의 데이터를 **한 테이블에** 넣고, 키 값에 접두사를 붙여 구분한다
```
PK          SK                  속성
USER#u1     PROFILE             name, email
USER#u1     ORDER#2026-11-01#o9 total, status
USER#u1     ORDER#2026-11-05#o12 total, status
ORDER#o9    ITEM#p1             qty, price
```
- `Query(PK="USER#u1", SK begins_with "ORDER#")` → 사용자의 주문 목록을 **날짜순으로 한 번에**
- 장점 : 관련 데이터를 요청 한 번으로 가져옴 (JOIN 대신)
- 단점 : 키 구조를 읽기 어렵고, 조회 패턴이 바뀌면 고치기 어렵다
- ==? 꼭 단일 테이블이어야 할까? 서비스가 작고 조회 패턴이 자주 바뀐다면 테이블을 나누는 편이 나을 수도 있다.==

# 4. 장애 상황 — 핫 파티션과 요청 제한
## 4.1 핫 파티션
- **특정 파티션 키에 요청이 몰리는** 상황. 테이블 전체 용량이 남아도 그 파티션의 한계(쓰기 1,000 WCU/s)를 넘으면 막힌다
- 나쁜 파티션 키의 예
	| 키 | 문제 |
	| --- | --- |
	| `date` (오늘 날짜) | 오늘의 모든 쓰기가 파티션 하나로 |
	| `status` (PENDING / DONE) | 값이 몇 개뿐 → 파티션이 몇 개밖에 안 쓰임 |
	| 인기 상품 `PRODUCT#best` | 이벤트 때 한 키에 폭주 |
- 대처
	- **값의 종류가 많은 키**를 고른다 (`userId`, `orderId`)
	- **쓰기 샤딩** : 키 뒤에 임의의 숫자를 붙여 나눠 쓴다 → `DATE#2026-11-08#3`. 대신 읽을 때 샤드 수만큼 조회해서 합쳐야 한다
	- 읽기가 몰리면 **DAX**(DynamoDB 전용 인메모리 캐시)나 앞단 캐시를 둔다
- DynamoDB에도 **적응형 용량(adaptive capacity)**이 있어 어느 정도는 자동으로 흡수하지만, 키 설계를 대신해 주지는 않는다

## 4.1-2 처리량 관리는 어떻게 동작하나 (내부 동작)
> 출처 : USENIX ATC 2022 논문 『Amazon DynamoDB: A Scalable, Predictably Performant, and Fully Managed NoSQL Database Service』, AWS 개발자 가이드. 세부 수치는 AWS가 바꿀 수 있다.
> 👉 애니메이션 설명 : [DynamoDB 처리량 관리 (인터랙티브)](https://claude.ai/artifact/PZUyjzDZxScfDofyj3LDMw)

DynamoDB는 "용량 문제를 어떻게 풀었나"의 역사로 보면 이해하기 쉽다. **문제가 생기고 → 다음 장치가 그 문제를 푸는** 순서다.

### 🥐 쉽게 말하면 — 빵집 이야기
| 빵집 | DynamoDB |
| --- | --- |
| 빵집 | 테이블 |
| 계산대 | 파티션 |
| 손님 | 요청 |
| 번호표 | 토큰 (1장 = 1 WCU) |
| "잠깐 기다려 주세요" | 요청 제한 |
| 상가 건물 | 스토리지 노드 |

1. **처리율 할당** : 빵집은 1초에 손님 400명까지 받는다. 계산대가 4개라 "계산대마다 100명씩" 똑같이 나눴다. 그런데 손님이 전부 1번 계산대에만 줄을 서면, 다른 계산대는 노는데 1번만 줄이 길어진다.
2. **토큰 버킷** : 계산대 앞 번호표 통에 1초마다 번호표 100장이 채워진다. 번호표를 뽑아야 계산할 수 있고, 통이 비면 기다려야 한다.
3. **버스팅** : 손님이 적을 때 남은 번호표를 저금통에 모아 둔다(최대 5분치). 손님이 갑자기 몰리면 저금통에서 꺼내 준다. 계속 몰리면 저금통도 빈다.
4. **적응형 용량** : 매니저가 "1번 줄이 기네!" 하고 1번에 번호표를 더 보낸다. 하지만 줄이 이미 길어진 다음에야 알아챈다.
5. **GAC** : 번호표를 계산대마다 나눠 주지 않고 빵집 입구에서 한 통으로 나눠 준다. 빵집 전체 400장 안이면 어느 계산대로 가든 바로 계산한다.
6. **선제적 관리** : 건물이 붐비기 시작하면 문제가 터지기 전에 가게 하나를 한가한 건물로 이사 보낸다. 줄을 나눌 때는 손님 수가 반반이 되는 곳에서 자른다. 단, 손님 한 명이 빵 1,000개를 주문하면 줄을 나눠도 소용없다.

> 한 줄 정리 : 결국 **손님이 처음부터 고르게 퍼지게 만드는 것(파티션 키 설계)**이 제일 중요하다.

### ① 처리율 할당 — 테이블 용량을 파티션에 똑같이 나눠 줌 (초기 설계)
```
테이블 400 WCU, 파티션 4개 → 파티션마다 100 WCU
```
- 파티션 하나의 상한 : 쓰기 1,000 WCU / 읽기 3,000 RCU
- **문제 1. 핫 파티션** : 요청이 한 파티션에 몰리면 테이블 전체는 여유가 있어도 그 파티션만 요청 제한에 걸린다
- **문제 2. 처리량 희석(dilution)** : 데이터가 커져 파티션이 둘로 쪼개지면 처리량도 반씩 나뉜다 → 파티션당 처리량이 점점 줄어든다

### ② 토큰 버킷 — 요청을 허용할지 정하는 방법
- 버킷에 **초당 할당량만큼 토큰이 채워지고**, 요청은 비용(RCU/WCU)만큼 토큰을 꺼내 쓴다
- 토큰이 없으면 → 요청 제한(throttle)
- 버킷이 넉넉하면 **잠깐의 폭주는 받아 주고**, 길게 보면 평균 속도를 할당량 이하로 유지한다
- DynamoDB는 여러 단계에 버킷을 둔다 : **파티션 버킷**(할당량), **버스트 버킷**, **스토리지 노드 버킷**(노드 하나가 과부하되지 않도록)

#### Q. 토큰 버킷은 그냥 "전체 총량 제어"가 아닌가? 왜 효율적이지?
- 총량만 제어하는 게 아니라 **평균 속도와 순간 최대치를 동시에** 제어한다. 다른 방법과 비교하면 차이가 보인다 (할당량 100/초 기준)

| 방법 | 동작 | 문제 |
| --- | --- | --- |
| **고정 창 카운터** ("1초에 100개") | 매 초 0으로 초기화 | **경계 문제** : 0.9~1.0초에 100개 + 1.0~1.1초에 100개 → 0.2초 사이에 **200개**가 들어온다. 총량은 지켰지만 서버는 순간적으로 2배 부하를 받는다 |
| **일정 간격** (10ms마다 1개, 리키 버킷) | 요청 간격을 고정 | **폭주를 하나도 허용하지 않음** : 화면 하나 열 때 요청 30개가 한꺼번에 오면, 평균은 한참 낮아도 29개가 거절된다 |
| **토큰 버킷** (채우는 속도 r, 통 크기 b) | 토큰이 있으면 통과 | 위 둘의 중간. 어떤 시간 t를 잡아도 통과량이 **b + r·t 이하**로 보장된다 |

- 손잡이가 두 개다
	- **r (채우는 속도)** = 길게 봤을 때의 평균 → 비용·용량 계획
	- **b (통 크기)** = 한 번에 받아 줄 수 있는 최대 폭주 → 서버 보호
	- 고정 창 카운터는 b를 따로 정할 수 없고, 일정 간격 방식은 b가 사실상 0이다
- **"놀고 있던 용량"을 쓰게 해 준다** : 한동안 조용했다면 토큰이 쌓여 있으니 갑작스러운 요청을 받아 준다. 실제 트래픽은 대부분 들쭉날쭉하므로, 평균은 지키면서 **불필요한 거절을 줄인다** → 이용률이 높아진다
- **구현이 싸다** : 키 하나당 숫자 두 개(남은 토큰, 마지막 갱신 시각)만 저장하면 된다
	```
	tokens = min(b, tokens + r × (now - last))   // 요청이 올 때 한 번에 계산
	last = now
	if tokens >= cost: tokens -= cost; 통과
	else: 거절
	```
	- 타이머로 토큰을 계속 채울 필요가 없고, 요청 기록을 다 저장하는 방식(슬라이딩 로그)보다 메모리가 훨씬 적다
	- 그래서 DynamoDB처럼 **파티션마다, 노드마다, 라우터마다** 버킷을 수없이 둘 수 있다
- 쉽게 말하면 : 고정 창은 "1초마다 번호표 100장을 새로 뿌리는 것"이라 1초가 바뀌는 순간 손님이 한꺼번에 들어올 수 있다. 토큰 버킷은 번호표가 **조금씩 계속** 채워지고 통 크기 이상은 쌓이지 않아서, 언제 봐도 한꺼번에 들어오는 손님 수에 상한이 있다.

#### Q. 토큰의 정체는 뭘까?
- **실체가 있는 물건이 아니라 메모리에 있는 숫자 하나**다. 뜻은 "지금 더 처리해도 되는 일의 양"(남은 허용량)
- 토큰 1개 = **일 1단위를 해도 된다는 허락**
	- DynamoDB에서는 단위가 용량 단위다 : 쓰기 토큰 1개 = 1 WCU(1KB 쓰기 1번), 읽기 토큰 1개 = 1 RCU(4KB 강한 일관성 읽기 1번)
	- 그래서 요청마다 꺼내는 토큰 수가 다르다 : 3KB 쓰기 → 3개, 4KB 최종 일관성 읽기 → 0.5개, 트랜잭션 쓰기 → 2배
- "토큰이 채워진다"도 실제로 무언가가 만들어지는 게 아니다. 요청이 올 때 **지난 시간 × 채우는 속도**만큼 숫자를 더하는 계산일 뿐이다
	```
	버킷 = { tokens: 37.5, last: 12:00:00.120 }   ← 저장되는 것은 이 두 값뿐
	```
- 어디에 있나 (DynamoDB)
	| 위치 | 그 숫자가 뜻하는 것 |
	| --- | --- |
	| 스토리지 노드의 파티션 버킷 | 이 파티션이 더 처리해도 되는 양 |
	| 스토리지 노드 버킷 | 이 노드(서버)가 더 버틸 수 있는 양 |
	| GAC 서비스 | 이 테이블 전체가 더 쓸 수 있는 양 |
	| 요청 라우터의 작은 버킷 | GAC에게서 미리 받아 온 몫. "토큰을 받아 온다" = 숫자를 나눠 받는다 |
- 헷갈리기 쉬운 다른 "토큰"과는 관계없다
	- 인증 토큰(JWT, API 키) : "나는 누구다"를 증명하는 문자열
	- LLM 토큰 : 글자를 쪼갠 단위
	- 처리율 제한의 토큰 : **"얼마나 더 해도 되나"를 세는 숫자**
- 쉽게 말하면 : 번호표는 진짜 종이가 아니라, 계산대 옆 **칠판에 적힌 숫자 하나**다. 손님이 오면 숫자를 하나 지우고, 시간이 지나면 숫자를 늘린다. 숫자가 0이면 "잠깐 기다려 주세요".

### ③ 버스팅 — 안 쓴 용량을 모아 뒀다가 쓰기
- 파티션이 할당량보다 적게 쓰면, 남은 용량을 **최대 300초(5분) 분량까지** 모아 둔다
- 갑자기 요청이 몰리면 모아 둔 용량으로 할당량을 넘겨서 처리한다
- 단, 그 파티션이 올라가 있는 **스토리지 노드에도 여유가 있어야** 쓸 수 있다 (노드 버킷도 확인)
- 한계 : **짧은 폭주**에만 효과가 있다. 계속 몰리면 금방 바닥난다

#### Q. 버스팅 = "단기 오버프로비저닝"이란?
- **오버프로비저닝(over-provisioning)** : 필요한 것보다 용량을 넉넉하게 잡아 두는 것
	- 보통은 사용자가 최고치에 맞춰 할당량을 높게 잡는 것을 말한다 → 폭주는 버티지만 **평소에도 최고치 비용을 낸다**
- 버스팅은 이걸 **잠깐만, 공짜로** 해 주는 셈이다 → 할당량 100인 파티션이 몇 초~몇 분 동안 100보다 많이 쓰게 해 준다
- 이게 가능한 이유 : 스토리지 노드 쪽에 원래 **여유 용량**이 있기 때문이다
	- 노드 하나에는 여러 테이블의 파티션이 같이 올라간다
	- 모든 파티션이 **동시에** 자기 할당량을 다 쓰는 일은 드물다 → 노드 전체로 보면 항상 남는 용량이 있다
	- 버스팅은 이 남는 용량을 **잠깐 빌려 쓰는 것**이다. 그래서 파티션 버스트 버킷에 토큰이 있어도 **노드 버킷에 여유가 있어야** 쓸 수 있다
- 그래서 버스팅은 **보장이 아니라 최선의 노력(best effort)**이다
	- 같은 노드의 다른 파티션도 바쁘면 못 빌린다
	- 설계할 때 "버스트가 있으니 할당량을 낮게 잡아도 된다"고 기대하면 안 된다
| | 사용자가 하는 오버프로비저닝 | 버스팅 (단기 오버프로비저닝) |
| --- | --- | --- |
| 기간 | 항상 | 잠깐 (최대 300초 분량) |
| 비용 | 최고치만큼 계속 냄 | 추가 비용 없음 |
| 보장 | 보장됨 | **보장 안 됨** (노드에 여유가 있을 때만) |
| 용도 | 예측 가능한 큰 트래픽 | 예측 못 한 짧은 폭주 흡수 |
- 쉽게 말하면 : 계산대마다 직원 수는 정해져 있지만, 건물에는 **여러 가게가 같이 쓰는 공용 직원**이 몇 명 있다. 우리 계산대에 손님이 잠깐 몰리면 공용 직원을 빌려 온다. 단, 옆 가게도 바쁘면 빌릴 수 없다.

### ④ 적응형 용량 (Adaptive capacity) — 핫 파티션에 용량을 더 줌
- 동작 순서
	1. 테이블을 계속 지켜보다가
	2. **요청 제한이 생겼는데 테이블 전체로는 할당량을 넘지 않았다면**
	3. 제한에 걸린 파티션의 할당량을 **비례 제어 방식으로 올려 준다** (테이블 할당량을 넘으면 다시 내린다)
	4. 용량이 늘어난 파티션은 여유 있는 스토리지 노드로 옮긴다
- 한계 : **요청 제한이 생긴 뒤에야** 동작한다(사후 대응). 그 사이에는 사용자가 실패를 겪는다
- 지금의 AWS 문서 기준 : 적응형 용량은 **기본으로 켜져 있고 즉시** 동작한다. 자주 접근하는 항목을 **별도 파티션으로 떼어내기**(split for heat)도 한다

### ⑤ 파티션 간 관리 — 글로벌 승인 제어 (GAC, Global Admission Control)
- 생각을 바꿈 : 용량을 **파티션 단위가 아니라 테이블 단위로** 관리한다
- 동작
	- GAC 서비스가 테이블별 토큰 버킷을 관리한다
	- 요청을 받는 **요청 라우터**는 자기만의 작은 토큰 버킷을 갖고, 몇 초마다 GAC에서 토큰을 받아 온다
	- 그래서 **테이블 전체 할당량을 넘지 않는 한**, 어느 파티션에 몰리든 처리할 수 있다
	- 파티션 버킷은 그대로 남겨 **상한**으로 쓴다 (스토리지 노드 보호)
- 효과 : 적응형 용량처럼 "제한이 생긴 뒤에" 올리는 게 아니라, **처음부터** 테이블 용량을 파티션 사이에서 나눠 쓴다

### ⑥ 선제적 파티션 관리 — 문제가 생기기 전에 미리 움직임
- **노드 간 균형 맞추기** : 스토리지 노드 하나에는 여러 테이블의 파티션 복제본이 올라간다
	- 각 노드는 자기 처리량과 데이터 크기를 스스로 감시한다
	- **노드 최대 용량의 일정 비율을 넘으면** 옮길 후보 파티션을 보고하고, 관리 시스템이 덜 바쁜 노드로 옮긴다
	- → 동시에 몰리는 파티션들이 한 노드에 모여 있어서 생기는 과부하를 **미리** 막는다
- **사용량 기준 분할 (split for consumption)** : 파티션 처리량이 기준을 넘으면 쪼갠다
	- 분할 지점은 키 범위의 가운데가 아니라 **실제 요청이 몰린 키 분포를 보고** 고른다 → 요청이 반씩 나뉘도록
	- 쪼개도 소용없는 경우는 쪼개지 않는다 : **항목 하나에만 몰릴 때**, 키를 **순서대로** 접근할 때 (예: 타임스탬프 키로 계속 새 값 쓰기)
- **온디맨드 모드** : 실제 사용량을 보고 용량을 잡는다. **직전 최고치의 2배까지는 바로** 받아 주고, 넘으면 분할로 늘린다

## 4.2 요청 제한 (Throttling)
- 한계를 넘으면 `ProvisionedThroughputExceededException` 또는 `ThrottlingException`
- AWS SDK는 **지수 백오프로 자동 재시도**한다 → 재시도가 쌓여 지연이 길어지는 것이 실제 증상
- 모니터링할 CloudWatch 지표 : `ThrottledRequests`, `ConsumedReadCapacityUnits` / `ConsumedWriteCapacityUnits`, 그리고 **GSI의 요청 제한**

## 4.3 함께 알아 둘 기능
| 기능 | 용도 |
| --- | --- |
| **Streams** | 항목 변경 이벤트를 24시간 보관 → Lambda로 후처리 (검색 인덱스 갱신, 집계, 알림) |
| **TTL** | 만료 시각이 지난 항목을 **무료로** 자동 삭제. 즉시는 아니고 보통 며칠 안에 지워지므로, 읽을 때도 만료 여부를 확인 |
| **Global Tables** | 여러 리전에서 동시에 쓰기. 충돌하면 **마지막에 쓴 값이 이긴다** |
| **PITR** | 최근 35일 안의 원하는 시점으로 복구 → 5장 Q4의 "백업·복구" |

# 5. 직접 해 보기 — 장바구니 테이블 설계
## 5.1 조회 패턴부터 적는다
| # | 조회 패턴 | 연산 |
| --- | --- | --- |
| 1 | 사용자의 장바구니 전체 보기 | `Query(PK=USER#u1, SK begins_with CART#)` |
| 2 | 상품 담기 / 수량 바꾸기 | `UpdateItem(PK=USER#u1, SK=CART#p1)` + `ADD qty :n` |
| 3 | 상품 빼기 | `DeleteItem(PK=USER#u1, SK=CART#p1)` |
| 4 | 오래 방치된 장바구니 자동 정리 | 항목마다 `expiresAt` 저장 + TTL |
| 5 | 주문하기 (재고 차감 + 주문 생성 + 장바구니 비우기) | `TransactWriteItems` |

## 5.2 키 설계
```
PK            SK          속성
USER#u1       CART#p1     qty=2, price=12000, addedAt, expiresAt
USER#u1       CART#p7     qty=1, price=5000,  addedAt, expiresAt
PRODUCT#p1    STOCK       stock=40, version=12
ORDER#o100    META        userId=u1, total=29000, status=PAID
```

## 5.3 주문하기 트랜잭션
```
TransactWriteItems [
  Update  PRODUCT#p1 / STOCK : stock = stock - 2   조건: stock >= 2
  Update  PRODUCT#p7 / STOCK : stock = stock - 1   조건: stock >= 1
  Put     ORDER#o100 / META                        조건: 아직 없을 것 (attribute_not_exists)
  Delete  USER#u1 / CART#p1
  Delete  USER#u1 / CART#p7
]
```
- 재고가 하나라도 모자라면 **전부 실패** → 재고가 마이너스가 되지 않는다
- `attribute_not_exists`로 같은 주문이 두 번 생기는 것(중복 결제 재시도)을 막는다

# 5-2. 직접 해 보기 — 영상 이어보기 위치 저장
> 실제 OTT 서비스의 내부 구현이 공개된 것은 아니다. 아래는 **흔히 쓰는 설계를 재구성한 것**이다.

## 요구사항 → 조회 패턴
| # | 요구사항 | 연산 |
| --- | --- | --- |
| 1 | 영상을 다시 열면 보던 위치부터 재생 | `GetItem(PK=PROFILE#p1, SK=CONTENT#c9)` |
| 2 | 보는 중에 위치를 계속 저장 | `UpdateItem` (주기적으로) |
| 3 | 홈 화면 "이어보기" 목록 (최근에 본 순) | `Query` (최근 시청순 인덱스) |
| 4 | 다 본 영상은 목록에서 빼기 | 시청 비율 95% 이상이면 `finished = true` |
| 5 | 1년 넘게 안 본 기록은 정리 | TTL |

## 키 설계
```
PK            SK            속성
PROFILE#p1    CONTENT#c9    positionSec=1835, durationSec=3600,
                            lastWatchedAt=2026-11-08T21:10:05Z,
                            deviceId=tv-1, finished=false, expiresAt
PROFILE#p1    CONTENT#c3    positionSec=420,  durationSec=5400, ...
```
- 파티션 키를 `userId`가 아니라 **프로필 ID**로 둔다 (한 계정을 가족이 나눠 쓰므로)
- 목록을 최근 시청순으로 보여 주려면 정렬 키가 `lastWatchedAt`인 인덱스가 필요하다
	- **LSI**(PK=PROFILE#p1, SK=lastWatchedAt) : 파티션 키가 같으니 LSI가 딱 맞다. 단 테이블을 만들 때 같이 만들어야 한다
	- 또는 **GSI**(같은 키 구성) : 나중에 추가할 수 있지만 최종 일관성만 된다 → 목록이 1~2초 늦게 바뀌어도 괜찮으니 GSI도 충분하다

## 쓰기 — 가장 신경 써야 하는 부분
- 매초 저장하면 **시청자 수 × 초당 1번**의 쓰기가 생긴다 → 비용과 처리량 모두 낭비
- 보통은 이렇게 줄인다
	- 재생 중에는 **10~30초마다** 한 번 저장
	- **일시정지, 탐색(seek), 앱 종료, 다음 화로 넘어갈 때** 즉시 저장
- 저장 연산
```
UpdateItem
  Key: { PK: "PROFILE#p1", SK: "CONTENT#c9" }
  UpdateExpression:    "SET positionSec = :pos, lastWatchedAt = :now, deviceId = :dev"
  ConditionExpression: "attribute_not_exists(lastWatchedAt) OR lastWatchedAt < :now"
```
- 조건을 거는 이유 : **기기 여러 대, 늦게 도착한 요청** 문제
	- TV에서 보다가 폰으로 이어 봤는데, TV가 늦게 보낸 예전 위치가 나중에 도착해 덮어쓸 수 있다
	- "내 시각이 더 최신일 때만 쓰기"로 **옛 값이 새 값을 덮어쓰지 못하게** 한다
	- 시각 기준을 기기 시계로 둘지 서버 시계로 둘지도 정해야 한다 (기기 시계는 틀릴 수 있다)

## 왜 DynamoDB가 잘 맞나
- 조회가 거의 전부 **"이 프로필의 이 영상"** → 키 하나로 끝남
- 쓰기가 매우 많지만 프로필마다 고르게 퍼져서 **핫 파티션이 생기기 어렵다**
- 위치가 1~2초 늦게 반영돼도 괜찮다 → **최종 일관성으로 충분**하고 비용도 절반
- 여러 나라에 서비스한다면 Global Tables로 가까운 리전에서 읽고 쓴다 (충돌하면 마지막에 쓴 값이 이기는데, 이어보기에서는 그게 원하는 동작)

# 실무에서는 주로 어떨 때 쓰나?
## 공통점 : "단순한 조회, 많은 트래픽"
- 대부분 **키 하나로 읽고 쓰는** 데이터다 (누구의 무엇)
- 트래픽이 크거나 **갑자기 몰린다**
- 응답이 늦으면 바로 사용자 경험이 나빠진다

## 쓰임새별 정리
| 쓰임새 | 예 | 왜 DynamoDB인가 |
| --- | --- | --- |
| 사용자별 상태 저장 | 장바구니, 찜 목록, 이어보기 위치, 설정값 | 키 = `userId`. 사용자 수만큼 고르게 분산됨 |
| 세션·토큰 | 로그인 세션, 인증 토큰, 중복 요청 방지 키 | 키로만 조회 + TTL로 자동 만료 |
| 이벤트·시계열 기록 | IoT 센서, 위치 기록, 활동 로그 | 쓰기가 아주 많음. `기기ID + 시각`으로 범위 조회 |
| 상태 추적 | 주문·배송·결제 상태 | 단건 조회·갱신 위주. Streams로 상태 변경 알림 |
| 서버리스 백엔드 | Lambda + API Gateway | 커넥션 풀이 필요 없음 (HTTP 요청) → Lambda와 잘 맞음 |
| 메타데이터 | 파일 정보, 작업 상태 | 실제 파일은 S3에, 정보는 DynamoDB에 |

## 공개된 사례 (AWS 발표 기준)
- **Amazon** : 장바구니, 주문 등 쇼핑 핵심 기능. Prime Day에는 초당 1억 건이 넘는 요청을 처리했다고 발표
- **Disney+** : 시청 목록, 이어보기 위치
- **Zoom** : 2020년 사용자가 급증할 때 확장 수단으로 사용
- **Lyft** : 운행 중 위치 추적

## 실무에서 흔한 구조 : RDB와 함께 쓴다
```
            ┌──> MySQL / PostgreSQL : 회원, 결제, 정산 (JOIN·정합성이 중요)
API 서버 ──┤
            └──> DynamoDB          : 세션, 장바구니, 이벤트 로그 (트래픽이 큰 단순 조회)
```
- DynamoDB **하나로 모든 것을 하는 경우는 드물다**
- "핵심 데이터는 RDB에, 트래픽이 몰리는 일부만 DynamoDB로 뺀다"가 가장 흔한 시작점
