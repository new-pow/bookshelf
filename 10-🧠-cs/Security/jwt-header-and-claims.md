# 1. 먼저 짚고 갈 오해
| 오해 | 실제 |
| --- | --- |
| 페이로드는 암호화되어 있다 | JWS 형태의 JWT는 **Base64URL 인코딩만** 되어 있다. 누구나 디코딩해서 읽을 수 있다 |
| 서명이 있으니 안전하다 | 서명은 **무결성**(안 바뀌었다)만 보장한다. **기밀성**(숨김)은 없다 → 숨겨야 하면 JWE |
| JWT 헤더 = HTTP 헤더 | 다르다. JWT 헤더는 토큰 안의 **JOSE 헤더**(`alg`, `kid`...), HTTP 헤더는 요청의 `Authorization`, `DPoP` 등 |

```
eyJhbGciOi...  .  eyJpc3MiOi...  .  SflKxwRJSM...
└ JOSE 헤더 ┘     └ 페이로드  ┘     └  서명   ┘
   (Base64URL)       (Base64URL)    헤더+페이로드를 서명
```
- 헤더도 서명 범위에 포함되므로 **변조는 못 한다**. 하지만 **공격자가 처음부터 직접 만든 토큰**의 헤더는 마음대로다 → 헤더 값은 신뢰하지 않고 검증한다.

# 2. JOSE 헤더 — "추가"보다 "검증"
| 파라미터 | 역할 | 보안 포인트 |
| --- | --- | --- |
| `alg` | 서명 알고리즘 | 서버에서 **허용 목록으로 고정**. `none` 거부, RS256↔HS256 혼동 공격 방지 |
| `typ` | 토큰 타입 | `at+jwt` 처럼 **명시적 타입**을 쓰고 검증 → 토큰 혼동 방지 (3장) |
| `kid` | 키 식별자 | 키 로테이션용. **내 키 저장소(JWKS)에서만** 조회. 값을 파일 경로·SQL에 그대로 쓰지 않기 |
| `crit` | 반드시 이해해야 하는 확장 | 모르는 값이 있으면 거부 |
| `jku`, `jwk`, `x5u`, `x5c` | 토큰이 **자기 검증 키를 스스로** 알려줌 | ⚠️ 공격자가 자기 키를 넣을 수 있음 → 무시하거나 allowlist로만 |

- 대표 공격 예시
	- **`alg: none`** : 서명 없는 토큰을 그대로 통과시킴
	- **알고리즘 혼동** : RS256 공개키를 HS256의 비밀키처럼 써서 공격자가 서명을 만들어냄 → 라이브러리에 "이 키는 RS256 전용"을 명시
	- **`kid` 인젝션** : `kid: "../../dev/null"` 처럼 경로를 넣어 빈 키로 검증시키기

==? 우리 서비스의 검증 코드는 `alg`를 토큰 헤더에서 읽어 쓰나, 서버 설정으로 고정하나?==

# 3. `typ` 과 `at+jwt` 자세히
## 3.1 값별 의미
| `typ` 값 | 의미 | 보안 효과 |
| --- | --- | --- |
| `JWT` | "이건 JWT다" 라는 일반 표시 | 거의 없음. 라이브러리 기본값 |
| `at+jwt` | OAuth **액세스 토큰** (RFC 9068) | 있음. ID 토큰 등 다른 용도의 토큰을 API 호출에 못 쓰게 함 |
| `dpop+jwt` | DPoP 증명 (RFC 9449) | 액세스 토큰이 아니라 요청마다 붙이는 증명 |
| `xxx+jwt` | 서비스 자체 정의 타입 | 서버가 검증하면 효과 있음 |

- 막는 공격 : **토큰 혼동(token confusion)**
	- 같은 키로 액세스 토큰, 리프레시 토큰, 이메일 인증 토큰을 서명한다면?
	- 이메일 인증 링크의 토큰으로 API를 호출할 수 있게 된다 → `typ`으로 구분하고 검증
- **들어 있는 것만으로는 효과 없음.** 받는 서버가 비교해야 의미가 있다.
	- 예) Spring Security `JwtTypeValidator`, `jose` 라이브러리의 `typ` 옵션
	- 직접 확인 : 같은 발급자의 다른 종류 토큰(예: 리프레시 토큰)으로 API 호출 → 거부되면 검증 중

## 3.2 `at+jwt` = RFC 9068 규격을 따른다는 선언
- 정식 미디어 타입은 `application/at+jwt`, 헤더에는 보통 `at+jwt`. 리소스 서버는 **둘 다** 받아야 한다.

| 구분 | RFC 9068 요구사항 |
| --- | --- |
| 헤더 | `typ` = `at+jwt`. `alg`는 `none` 금지, RS256 필수 지원 |
| 필수 클레임 | `iss`, `exp`, `aud`, `sub`, `client_id`, `iat`, `jti` |
| 선택 클레임 | `scope`, `auth_time`, `acr`, `amr`, `groups` / `roles` / `entitlements` |

- 토큰에 `at+jwt`를 넣는 건 **발급자(인가 서버)** 의 몫, 그걸 검증하는 건 **각 API 서버** 의 몫 → 서로 다른 팀 책임일 수 있다.

==? `typ: at+jwt`인데 필수 클레임 7개가 다 들어 있지 않다면, 규격을 "반만" 따르는 셈 아닐까?==

# 4. 페이로드 클레임
## 4.1 표준 등록 클레임 (RFC 7519) — 넣고, 검증까지
| 클레임 | 의미 | 막는 공격 |
| --- | --- | --- |
| `exp` / `nbf` / `iat` | 만료 / 사용 시작 / 발급 시각 | 탈취된 토큰을 오래 쓰기 (만료를 짧게) |
| `iss` | 발급자 | 다른 발급자가 만든 토큰을 받아들이기 |
| `aud` | 대상(이 토큰을 받을 서비스) | A 서비스용 토큰을 B 서비스에서 재사용 |
| `sub` | 주체(사용자) | — |
| `jti` | 토큰 고유 ID | 재전송(replay). 블랙리스트·1회용 처리의 키 |

## 4.2 확장 클레임 — 상황에 따라
| 클레임 | 출처 | 용도 |
| --- | --- | --- |
| `cnf` (`jkt`) | RFC 7800, RFC 9449 | 토큰을 클라이언트 키에 **바인딩**. 탈취해도 그 키 없으면 못 씀 |
| `scope`, `client_id` | RFC 9068 | 최소 권한 |
| `sid` | OIDC | 세션 단위 로그아웃·무효화 |
| `nonce` | OIDC | ID 토큰 재전송 방지 |
| `auth_time`, `acr`, `amr` | OIDC | 언제·어떤 강도로 인증했나 → 민감 작업 시 재인증 요구 |
| `ver` (커스텀) | 자체 정의 | 비밀번호 변경 시 버전을 올려 기존 토큰 일괄 무효화 |

## 4.3 넣으면 안 되는 것
- 개인정보, 비밀번호 해시, 내부 권한 상세 → 누구나 디코딩해서 읽을 수 있다
- 꼭 필요하면 JWE(암호화된 JWT) 또는 불투명(opaque) 토큰 + introspection

## 4.4 로그아웃해도 토큰이 살아 있는 문제 — 방법 비교
| 방법 | 원리 | 무상태(stateless) 유지 | 단점 |
| --- | --- | --- | --- |
| 짧은 `exp` + 리프레시 토큰 | 액세스 토큰은 몇 분만 유효 | ✅ | 만료 전까지는 여전히 유효 |
| `jti` 블랙리스트 | 무효화된 `jti`를 저장소에 기록 | ❌ (조회 필요) | 매 요청 저장소 조회 |
| `ver` / `sid` 비교 | 사용자·세션의 현재 버전과 비교 | ❌ (조회 필요) | 블랙리스트보다 저장량 작음 |

==? JWT의 장점이 "서버가 상태를 안 가진다"인데, 블랙리스트를 두면 세션 방식과 무엇이 다를까?==

# 5. HTTP 헤더 쪽 — Bearer vs DPoP
| 방식 | 요청 예시 | 특징 |
| --- | --- | --- |
| Bearer | `Authorization: Bearer <JWT>` | **가진 사람이 곧 주인**. 탈취에 약함 |
| DPoP | `Authorization: DPoP <JWT>` + `DPoP: <proof JWT>` | 요청마다 클라이언트 개인키로 서명한 증명을 첨부, 토큰의 `cnf.jkt`와 대조 |

- 브라우저 저장이라면 `HttpOnly; Secure; SameSite` 쿠키도 함께 고려 (XSS로 토큰 읽기 방지)

# 6. 리소스 서버 검증 체크리스트
1. `typ`이 `at+jwt` 또는 `application/at+jwt`인가 → 아니면 거부
2. `iss`가 신뢰하는 인가 서버인가
3. `aud`에 **이 API 자신**이 들어 있는가
4. 서명 확인 — `alg`는 허용 목록, 키는 인가 서버 JWKS에서 `kid`로 조회
5. `exp`가 지나지 않았는가 (`nbf`도)
6. `scope` 등으로 권한 판단
- 실무에서 가장 자주 빠지는 것 : **1번(`typ`)과 3번(`aud`)**

## 직접 확인하는 법
- 실제 토큰을 디코딩해서 위 표와 대조한다. 운영 토큰은 jwt.io 같은 외부 사이트에 붙여넣지 말고 로컬에서 디코딩한다.
```bash
echo '<토큰의 첫 번째 또는 두 번째 조각>' | tr '_-' '/+' | base64 -d 2>/dev/null; echo
```
